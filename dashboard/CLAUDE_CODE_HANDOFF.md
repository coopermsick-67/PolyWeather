# WeatherPicks — Claude Code handoff

_Last reviewed: 2026-09-03, after merging the two independent forecast backends into one._

## Product truth

WeatherPicks is an experimental daily-high weather research dashboard for
settlement-station markets. It is not betting, financial, or weather-safety
advice, and it must never claim a guaranteed edge, outcome, or profit. No
provider-specific market settlement contract, price, or ruleset has been
verified for any station yet — every forecast is deliberately labeled
`NO BET` / `EXPERIMENTAL / NO MARKET CONTRACT` until that changes. Do not
relax that default to make the product look more "actionable"; if you
disagree with the posture, raise it with the user rather than quietly
changing the code.

## Architecture: ONE forecast backend, not two

**This used to be two independent, drifting implementations of the same
forecast pipeline** — a real Python one (`server.py` + `dashboard_payload.py`,
scikit-learn/XGBoost via `joblib`) and a hand-written JavaScript
reimplementation inside the Cloudflare Worker (`create-worker.mjs`) that
re-fetched Open-Meteo directly and re-derived every feature and tree
prediction by hand. They had drifted to point at different trained models
and, at one point, the JS tree-traversal had every missing-value routing
backwards relative to the real model (confirmed against the actual deployed
artifact: 100% of 13,908 nodes). **That reimplementation has been removed.**

- `src/polyweather/` + `server.py` (deployed to Render per `render.yaml`) is
  now the **only** place forecasts are computed. It is real, tested
  (`tests/*.py`) `joblib`/scikit-learn/XGBoost inference against
  `artifacts/production_v3/xgb_residual_tmax.joblib` (20 stations).
- `dashboard/scripts/create-worker.mjs` builds a Cloudflare Worker that is now
  a **thin proxy in front of that Flask API**, plus everything Flask has no
  equivalent for: ChatGPT-Apps identity, the free-trial/paywall gate, and
  Stripe billing (checkout, portal, webhook) via D1 (`dashboard/db/schema.ts`).
  See `fetchFlaskDashboard()` / `liveDashboard()` in `create-worker.mjs` — do
  not add forecast computation back into this file. If the Worker needs a
  field the Flask payload doesn't have yet, add it to
  `dashboard_payload.py`'s `_assemble_payload()`/`_build_forecasts()` and let
  it flow through, rather than deriving it independently in JS again.
- `FORECAST_API_URL` (env var, defaults to `https://polyweather-api.onrender.com`
  — Render's auto-generated URL for the `polyweather-api` service in
  `render.yaml`) tells the Worker where that one backend lives. See
  `.env.example`.
- **Real, currently-unmitigated-in-infra risk of this merge:** Render's free
  tier spins the API down after inactivity; a cold start plus live
  NWS/Open-Meteo fetches can take 30-50s. `FORECAST_API_TIMEOUT_MS` in the
  Worker is set to 55s (just under gunicorn's own `--timeout 60`) to give a
  slow-but-alive backend a chance to win the race, but a very slow cold start
  can still surface as an error to the end user. If this matters in practice,
  either upgrade the Render plan or add a scheduled keep-alive ping — this
  has not been done.
- `xgb-worker-model.json` and `scripts/export_worker_model.py` are **deleted**
  — they were only for the removed JS reimplementation. `backtest-worker.js`
  (client-side historical backtest scoring against the static
  `backtest-data.json` archive) is unrelated and unaffected; it never used
  the live model artifact.

## Identity / security

- `identityFrom()` in `create-worker.mjs` reads `oai-authenticated-user-id`/
  `-email` headers. **These are meaningless unless `IDENTITY_GATEWAY_SECRET`
  is configured** as a real Worker secret, with the trusted upstream gateway
  (whatever actually authenticates the ChatGPT-Apps caller) attaching the
  identical value as `x-weatherpicks-gateway-secret` on every forwarded
  request. Without it, anyone who can reach the Worker's own URL directly can
  forge those two headers and impersonate any user, including an admin (by
  setting the admin's email) — full paywall bypass. This has been fixed in
  code (constant-time comparison, fails closed when the header doesn't match,
  loudly logs when the secret isn't configured at all) but **the secret
  itself has not been provisioned on real infrastructure** — do that before
  relying on this being safe in production.
- The Stripe webhook handler (`processStripeWebhook`) verifies signatures
  correctly (HMAC-SHA256, constant-time compare, 300s replay window) and
  records success only *after* the state mutation succeeds, not before — so
  a failed mutation can still be retried by Stripe rather than being silently
  marked "handled." Keep that ordering if you touch this function.

## Current implementation (frontend/data)

- React/Vite frontend in `src/`. The public backtest scores immutable
  archived rows (`dashboard/public/backtest-data.json`, generated by
  `scripts/export_backtest_data.py`) in a browser Worker
  (`backtest-worker.js`) — static historical scoring, not an on-demand
  forecast replay. `BacktestWorkspace.jsx` rejects a start date after the end
  date client-side before ever spawning that worker.
- The residual model (`artifacts/production_v3/model_manifest.json`) is
  historically evaluated for all 20 configured settlement stations. Preserve
  the `SHADOW_ONLY` disclosure — `_acceptance()` in `backtest.py` requires
  every configured station to beat NBM, not a small subset.
- Date validation (both `dashboard_payload.py`'s `validate_dashboard_date`
  and the Worker's `targetDateForRequest`, sharing logic via
  `dashboard/src/workerShared.js`) uses the *earliest* local "today" across
  every configured station's own timezone as the lower bound, not just
  America/New_York — a West Coast station's local day hasn't rolled over yet
  for up to ~3 hours after Eastern already has. Don't re-anchor this to a
  single timezone.
- `dashboard/src/workerShared.js` is the tested (`node --test`) source of
  truth for the Worker's date/timezone/constant-time-comparison helpers;
  `create-worker.mjs` splices its text in at build time rather than
  hand-duplicating it. If you need to change that logic, change it there —
  editing the generated `dist/server/index.js` copy directly will be
  overwritten on the next build.
- CI (`.github/workflows/test.yml`) runs `pytest` and `npm test` + `npm run
  build` on every push/PR to `main`.

## Guardrails

- Preserve `WeatherPicks` in all user-facing UI and metadata. The Python
  `polyweather` package is intentionally not renamed yet.
- Keep the landing disclaimer adjacent to all pick-oriented copy.
- `server.py`'s `/api/dashboard` route is deliberately fault-isolating: one
  station's upstream failure should degrade that station only, never 500 the
  whole response. Preserve that shape in `dashboard_payload.py`.
- Run `pytest` (repo root) and `npm test` (in `dashboard/`) before
  committing — both are fast and both run in CI.
- Do not reintroduce a second forecast implementation. If the Worker needs
  something Flask's payload doesn't provide, extend the Flask payload.

## Known open items

1. `IDENTITY_GATEWAY_SECRET` needs to actually be provisioned on the real
   Cloudflare/ChatGPT-Apps infrastructure — the code-level fix is done, the
   infra step is not.
2. Render free-tier cold starts are a real latency/timeout risk for the
   now-merged architecture (see above).
3. No provider-specific market-settlement contract/pricing exists yet
   (deliberately: everything is `NO BET` until one is verified). Building
   that out is a large, separate feature, not a bug fix.
4. Add browser tests for the backtest worker's lifecycle (cancellation,
   error surfacing) and for the Worker's auth/billing routes — currently the
   Worker's HTTP surface has no automated test coverage beyond the shared
   date/security helpers in `workerShared.test.js`.
